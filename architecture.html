How TrojanAI works

TrojanAI is a USC question-answering assistant. Think of it as three people working together: a student asks, a researcher finds the answer, and an editor checks it before it is shown.

The whole idea in one picture

Student types a question │ ▼ app.py shows the chat screen │ ▼ engine.py sends the question to OpenAI │ ├── searches current USC websites │ ├── writes an answer with source links │ ├── asks a second model request: “Is this answer correct and useful?” │ └── fixes it once if the review finds a problem │ ▼ Student sees the answer, sources, and any warnings
In short: it does not simply ask an AI to answer from memory. It researches first, checks the draft, and tells the student when something is still uncertain.

What happens when a student asks a question?

1

Ask

The student enters a question, such as “When can I drop this class?”

2

Remember

The app adds recent chat messages, the optional academic profile, and today’s Los Angeles date.

3

Look up

OpenAI searches and opens relevant USC pages. Search is restricted to USC domains.

4

Check

A separate review looks for wrong dates, missing sources, and an answer that is not actionable.

5

Show

The student gets the answer, clickable sources, the research date, and warnings if needed.

The three simple parts

1. Chat screen — app.py

Loads the configured API key, displays the page, collects the question, stores the visible conversation during the session, and displays the answer and sources.

2. Brain — engine.py

Prepares the question, calls OpenAI, runs web research, turns citations into links, asks for a review, and returns one final result.

3. Test bench — tests and evaluate.py

Checks that the workflow behaves correctly. Live evaluation is separate and requires deliberate confirmation because it uses the API.

How the “research and review” works

First request: write the answer

The research instructions tell the model to search current USC pages, open the relevant pages, match the right year and session, and include the exact source beside important claims. The response must use fixed fields such as answer, assumptions, key details, steps, notes, and one follow-up question.

Second request: challenge the answer

A different prompt receives the draft and independently checks five things: directness, factual support, specificity, context, and next steps.

Optional repair

If the answer fails, the engine gives the review back to the research model. It creates a new cited answer and checks it one more time. It stops after that one repair.

What the student sees

  1. The answer in the chat.
  2. Clickable source links, labeled as USC or external.
  3. The research date and number of API requests.
  4. Review details and warnings when evidence is missing or a problem remains.

How consistent formatting is enforced

The model does not decide the page layout. It returns structured information, and the Python program places that information into one template:

### Answer ### Assumptions (shown when needed) ### Key details (always a consistent table) ### What to do next (numbered steps) ### Important notes (warnings and limitations) ### One follow-up question (shown only when needed)

This works across many question types because the fields are general. A deadline uses the key-details table for dates; a transfer question uses it for requirements; a private-record question uses it for access limitations. The model supplies the content, while format_answer() controls the presentation.

How follow-up questions work

First turn: “I want to transfer to Viterbi. What should I prepare?” │ ▼ Answer general preparation + ask: “Which Viterbi major and transfer term are you targeting?” │ ▼ Second turn: “Computer Science for Fall 2027.” │ ▼ The engine sends the previous answer, the new clarification, and the conversation history back for a specific research answer.

Missing information is treated as context to collect, not automatically as an error. The conversation keeps the previous answer, so the student can answer the follow-up naturally in the next message.

Why the answer may contain a warning

The program is deliberately cautious. A good-looking score cannot hide a missing official source or a missing date in a deadline answer.

No official citation → warningDeadline without a date → warningUnclear review → fail safelyOne repair only

Important: TrojanAI cannot log into student systems. It cannot read STARS, WebReg, private USC portals, or medical records, and it should never be given passwords, USC IDs, API keys, or private account details. The API key is loaded from the environment or Streamlit secrets.

How much work does one question use?

Review off: one research request.

Review on and answer passes: two requests — write, then check.

Review on and answer needs repair: up to four requests — write, check, repair, check again.

Technical details for developers

answer() is the main coordinator. payload() bounds the context and adds the Los Angeles date. request() calls the OpenAI Responses API with required USC-only web search, store=False, bounded tool calls, and a strict JSON schema. structured_answer() validates the model fields, while format_answer() creates the fixed Markdown layout. parse_audit() reads the review JSON, while enforce_checks() catches missing citations and dates that a model score might overlook.

The deterministic tests cover context handling, URL safety, citation conversion, repair behavior, privacy settings, incomplete responses, and Streamlit reruns.
